# SQLite для replay-защиты

`replay.SQLite` реализует [`httpsig.ReplayStore`](../httpsig/README.md) для одного verifier namespace. SQLite выполняет проверку nonce, очистку истёкших записей, проверку квоты caller/namespace и запись в одной транзакции `BEGIN IMMEDIATE`. Успешное резервирование возвращается после commit в WAL с `synchronous=FULL`. Квота caller общая для обоих signing legs. Повтор возвращает `httpsig.ErrReplay`, квота caller — `httpsig.ErrReplayCallerQuota`, общая квота или отказ хранилища — `httpsig.ErrReplayUnavailable`.

## Provisioning и запуск

1. Выделите отдельный файл БД на локальной файловой системе и настройте права на каталог, DB, WAL и SHM. Все входящие каналы экземпляра используют одно хранилище и namespace. Разные реплики получают собственные файлы.
2. Создайте случайную 32-байтовую epoch. Храните ожидаемое значение в доверенном control state вне БД. `InitializeSQLite` выполняется явно для новой установки. Он создаёт файлы только на свободном пути, включая проверку прежних sidecars. `OpenSQLite` открывает существующую пару DB/WAL и сверяет epoch, схему и счётчики квот.
3. После каждого `OpenSQLite` вызов `Ready(ctx)` остаётся закрытым минимум 120 секунд. Запросы с `created` ранее начала барьера отклоняются. После барьера readiness также требует актуальных control/revocation данных проверяющего runtime. Передайте store и тот же namespace через `delivery.HandlerConfig.ReplayStore` и `ReplayNamespace`.
4. Укажите допущенный signed RPS, burst и ёмкость по формуле `150 × RPS + burst`. Квота caller должна быть меньше общей ёмкости. Runtime применяет ограничения скорости до криптографической проверки. Очистка в `Reserve` и отдельный вызов `Prune` удаляют максимум 256 истёкших записей за транзакцию. Активные записи сохраняются включительно до `RetainUntil`.

DB/WAL/SHM проверяются во время работы. Потеря или замена файла и откат сохранённой отметки времени блокируют дальнейший допуск текущим экземпляром. Чистое закрытие сохраняет WAL, чтобы штатный перезапуск можно было отличить от пропажи файла. При откате системных часов запись блокируется до достижения сохранённого времени.

При потере state остановите verifier. Восстановите актуальные отзывы, установите новую epoch в доверенном control state и выполните согласованную процедуру восстановления. Для сброшенного namespace используйте новый путь, сохраните старые файлы для проверки и опубликуйте recovery barrier в control state для всех verifier. Внешние процедуры восстановления control/revocation state и проверку локального диска выполняет развёртывание.

Тесты проверяют реальную SQLite, конкурентные транзакции с двух соединений, повтор после чистого перезапуска и после принудительного завершения процесса на включительной границе, квоты, откат часов, отказ записи и отсутствие WAL. Тесты с выключением питания, оценка пропускной способности и PostgreSQL остаются отдельными этапами.
