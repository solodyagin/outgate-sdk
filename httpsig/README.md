# Outgate HTTP signatures

`httpsig` реализует фиксированный HMAC-SHA256 профиль protocol §9, основанный на [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) и [Structured Fields RFC 8941](https://www.rfc-editor.org/rfc/rfc8941.html). Это самостоятельный пакет SDK, использующий standard library и bounded helpers из protocol/v1. Он не является общим RFC signature engine, middleware или готовым production verifier.

## Подписание

`New(Config{Leg: Call})` создаёт production профиль outgatecall; Leg Gateway выбирает outgategateway. Development включается явно. AttributeHeaders — копируемый allowlist дополнительных пользовательских заголовков, максимум 16; reserved/обязательные поля и hop-by-hop имена в нём запрещены.

Request содержит точные Method, Scheme, Authority, RawURI и ordered Header pairs. Scheme обязателен: https в production, http/https в development; он берётся из проверенного transport context. Authority — исходный прикладной Host/port, RawURI — публичный escaped URI до strip/rewrite. Список Headers не содержит второго Host: HTTP adapter должен перенести его в Authority и заранее отклонить duplicate Host/framing ambiguity. Компонент @authority по RFC lower-case-ит hostname и исключает default port схемы, не меняя request. Подпись сохраняет регистр method, escaping и порядок query; отсутствующий/пустой query даёт `?`. Body в API отсутствует и никогда не читается. Общие HTTP framing/Content-Length/Upgrade semantics остаются обязанностью HTTP adapter.

Sign(request, keyID, secret, now) возвращает пару SignatureInput/Signature с новым crypto/rand nonce из 16 bytes и expires=created+60. Добавить возвращённые поля к запросу обязан adapter. SignWithParams предназначен для deterministic vectors и callers с отдельным безопасным nonce generator. Secret должен содержать минимум 32 bytes и поступать из pinned keyring нужного leg/caller; пакет не выбирает ключи из запроса. Уже подписанный request не перезаписывается. Запрос, headers и secret не изменяются; бизнес-повторы автоматически не выполняются.

SignatureBase проверяет фиксированный список/порядок компонентов и возвращает base/canonical Signature-Input без HMAC. В production обязательны hop-limit 1…8, deployment-grant-id и при user context — assertion. Gateway leg дополнительно включает instance/version/prefix. Discovery revision, если присутствует, всегда покрывается подписью. Manifest — компактный JSON-массив отсортированных lower-case имён; user context содержит как минимум x-user-id/x-user-roles, background не содержит user/attribute fields. Подписанные identity fields строго single-valued, без leading/trailing OWS и CTLs. Неизвестные trusted Outgate/User/Tunnel поля отклоняются.

RFC 9421 требует ASCII field values в signature base: raw non-ASCII identity values отвергаются. Например, Unicode roles можно представить JSON escapes (`["\u00e9"]`); точные подписанные bytes на приёме не пересериализуются. Кодирование plain user ID/attributes в HTTP и semantic equality с JWT/context проверяет будущий adapter; пакет не придумывает percent/base64 encoding. Default user limits из ТЗ: ID 128 bytes, 32 роли по 64 decoded UTF-8 bytes, 16 attributes по 1024 bytes, сериализованный context ≤8 KiB. Экранированные CTLs/непарные surrogates в JSON context запрещены. Полный field section, включая создаваемые подписи, ограничен 32 KiB и 256 парами; URI — 8192 bytes.

## Проверка и replay

Порядок интеграции обязателен:

1. Ограничить и разобрать HTTP headers до allocation; выполнить rate limit, transport/caller identity и grant checks. Сырые duplicate signature/identity fields нельзя предварительно потерять через Header.Get.
2. ParseSignatureInput даёт только недоверенные metadata для поиска ключа в pinned конфигурации leg/caller. Он не подтверждает identity или принадлежность keyid. Поддерживается ровно профиль Outgate: одна dictionary entry/inner list без component parameters, затем created/expires/nonce/keyid/alg в фиксированном порядке. Extra labels/params/duplicate components запрещены. RFC whitespace, integer parsing и optional byte-sequence padding обрабатываются перед canonical serialization; алгоритм всегда hmac-sha256.
3. Verify(request, expectedKeyID, secret, now) проверяет точный component profile, HMAC через constant-time comparison и временное окно (future/expiry skew по 30s, обе границы включены). Все ошибки безопасны и не содержат peer strings/keys/claims. Результат Verified подтверждает только криптографический профиль и время. Info — копия scalar fields, не trusted user context.
4. Независимо проверить JWT/issuer/audience/actor/sub/sid/roles/attributes, полномочия маршрута/delegation/revision, target и назначенные instance/version/mount. Сопоставить caller с transport identity и keyring. Наличие корректного HMAC не заменяет эти проверки; тестовый opaque assertion из corpus не становится JWT.
5. Только затем вызвать verified.Reserve(ctx, store, trustedNamespace, now), непосредственно перед dispatch. Повторная проверка времени не допускает reserve после долгой authorization. Нулевой Verified не может резервировать nonce. Никакого автоматического reserve при Verify нет.

ReplayKey включает leg + verifier namespace + caller + key ID + nonce. ReplayStore.Reserve обязан одной транзакцией проверить uniqueness и caller/global capacity, сохранить запись до expires+30 включительно и COMMIT до возврата nil. Живые записи не вытесняются. Ошибка downstream не удаляет запись; cancellation после возможного commit также не откатывает nonce. Duplicate возвращает ErrReplay, capacity/storage/integrity/commit/cancellation — безопасный ErrReplayUnavailable. Произвольные backend ошибки не публикуются вызывающему как SQL/credentials.

Production backend обязан быть durable и пройти recovery/integrity barrier из ТЗ (≥120s). Интерфейс не доказывает durability произвольного implementation и не предоставляет volatile fallback. SQL drivers, persistent schema/recovery, capacity configuration и runtime health пока отсутствуют. Test fake с mutex демонстрирует contract и concurrent duplicate rejection, не production persistence.

CanonicalField отдельно реализует RFC комбинацию обычных list-based полей с сохранением порядка и `, `; identity headers не проходят такую комбинацию и требуют одно точное значение. Obs-fold/CRLF/CTL запрещены общим HTTP контрактом. Подпись не покрывает body, Authorization или Cookie и не заменяет TLS либо прикладную авторизацию.

## Проверки

Все четыре неизменённых signatures.json vectors проверяются по точным base/input/signature bytes, включая development/production, background/user, HTTP/HTTP3/WebSocket, UTF-8 escaped URI, empty query и binding/revision. Отдельно проверяется нормативный RFC field-combination example. Негативные tests включают original tamper vectors, недопустимые metadata/context/условные компоненты, математически корректный MAC с неверным coverage/order, ключи/nonce/time/Structured Fields bounds, header budget с выходными signature fields, replay namespace/capacity/retention/ошибки и конкурентное reserve. FuzzSignatureInput и FuzzVerifyProfile — bounded parser/verifier fuzz targets. Эти проверки не доказывают JWT authorization, SQL recovery или transport integration.
